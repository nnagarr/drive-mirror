# The rulings of Drive Mirror v2

**Date:** 2026-10-21, amended 2026-10-22
**Branch:** `feature/drive-mirror-v2`, merged into `main` as a fast-forward
**Plan:** `docs/superpowers/plans/2026-10-21-drive-mirror-v2.md`
**Spec:** `docs/superpowers/specs/2026-10-21-drive-mirror-v2-design.md`

These are the decisions taken on the human partner's behalf where the spec,
the plan and the code were in tension. Each says what was decided, why, and
what it costs if it was wrong.

---

## Before any code was written

**1 — The four trees are not hardcoded in `src/`.** The plan's global
constraints said no drive letter may appear in the source, but its own
Task 2 specified a `defaultMirrors()` returning the four `E:\` roots.
*Decided:* `defaultMirrors()` was removed. The four trees are recovered from
the **manifest**, which already holds their names and roots, by
`mirrorConfigsFromManifest`. A fresh install starts with an empty mirror
list. *Cost if wrong:* a v1 user who has deleted their manifest has to
re-add the four folders by hand.

**2 — The default backup location, and a stale comment.** The default backup
is a sibling of the manifest, while the runner's comment claimed the backup
lives "outside the app's own directory". *Decided:* the default stays — the
spec chose "one copy beside the manifest, plus an optional second copy on
another drive". The **comment** was wrong, not the default. *Cost if wrong:*
a fresh install's first backup is on the same disk as the manifest and does
not survive a disk failure; the second copy on another drive is the one
that does.

**3 — Three minor findings about the settings store were carried into the
tasks that own the concept** rather than fixed in one place: a nullable
field that escaped the wrong-kind rule, array elements that were not
validated, and a merge that replaced `schedule.shape` wholesale.

**4 — The overlap rule includes two identical roots, and a removed mirror's
root stays reserved.** `validateMirror` skipped the overlap report
precisely when the two roots were equal, although `overlaps` already
treated equal roots as an overlap and `overlapMessage` already had a
message for it — that message was unreachable. *Decided:* equality counts,
and a removed mirror's root is reserved for its thirty days. *Cost if
wrong:* for thirty days after a mirror is removed, its root cannot be given
to a different mirror.

**5 — The strict name rule stays; the spec's reason for it was wrong.** The
spec said the mirror name is never written to the local disk. It is: it is
the directory name under the superseded archive, reached through
`sanitizePathSegment`. *Decided:* the strict Windows rule stands, and the
spec was corrected. *Cost if wrong:* a folder called `Sales: 2026` must be
renamed, or its Drive folder becomes `Sales- 2026`.

**6 — The backup copy is written atomically, from the same bytes as the
manifest.** A plain `writeFile` truncates the target first, so a crash
during a backup would destroy the previous good copy. *Decided:* the
serialisation and the atomic write live in one place and both the manifest
and every backup copy use them.

**7 — A re-approve waits its turn and takes the same lock as a run.** A
re-approve that interleaves with a run is written over by that run, so the
user's approval was lost silently. *Cost if wrong:* the re-approve button
refuses while a sync is going, and the user retries.

**8 — A run that cannot take the lock returns a summary carrying a report,
not an empty one.** An empty summary reads as "everything is up to date",
the opposite of the truth.

**9 — The summary bar is quiet only when a run changed nothing AND had
nothing to say.** *Cost if wrong:* the bar shows the details section for a
run that only had notes.

**10 — A run is blocked when the signed-in account is not the one that owns
the manifest, and the message names both accounts.** *Cost if wrong:* the
user cannot sync until they start a fresh manifest, which is a lot to ask.

**11 — A manifest whose `version` field is not a number is damaged, not
empty.** It used to be replaced wholesale by an empty one, which would
have lost every mirror, every file and every retired record it held.

**12 — `ScheduleShape` lives in `src/core/schedule.ts`** and is re-exported
from `src/main/settings.ts`, the pattern `MirrorConfig` already uses.

**13 — The `/TR` command quotes the path, not the flag.** The quotes exist
so a path with spaces stays one piece.

**14 — A scheduled launch does not take the single-instance lock.** The
lock is what makes a second launch quit, and a scheduled run must not quit
because the window happens to be open. *Cost if wrong:* two window
instances could open at once.

**15 — A schedule that has never run has nothing to catch up on**, so
switching it on does not sync straight away. *Cost if wrong:* the user
waits for the first slot.

**16 — The mirror list lives in the settings, so adding, changing and
removing a mirror are settings operations**; the runner owns the Drive
side — moving a folder, bringing a file back.

**17 — The renderer has no test setup and none was added.** The component
behaviour is covered by the core functions it calls, and adding jsdom was
out of scope.

**18 — The icon is shipped as an extra resource and sent to the renderer as
a data URL**, because the sandboxed renderer cannot read a file of its own.

## After the whole-branch review

The reviewer found two things that would have broken the app. Both are
fixed. The rest are in the commit messages of the two fixes, which say what
each one was.

**19 — The configured Drive destination was ignored by every run.** The
folder was resolved by the mirror's *name* under My Drive, so a mirror set
to `Archive/2026/Photos` went to `My Drive/Photos`, and changing the
destination moved the folder and then made the next run upload everything a
second time. *Decided:* the run resolves the path, and the stored folder id
wins, so a folder renamed in the Drive browser is honoured rather than
duplicated.

**20 — The Windows task was never taken away**, so switching the schedule
off left it firing and the app kept syncing after the user said stop.
*Decided:* the task is removed when the schedule is switched off or the
mechanism moves away from it, and a scheduled launch refuses to run when
the schedule is off.

## After the first public release

**21 — The app keeps no copy of anything.** The user asked for the
superseded store to go: a file that changes replaces the copy on Drive, and
a file that is deleted goes to the Drive trash. The whole mechanism is
removed — the archive, the fail-closed gate, the setting, the actions, the
folder. *Cost if wrong, and it is a real one:* **a replacement is not
reversible.** Drive keeps no history for ordinary files, so the version
that was on Drive before is gone once the new one goes up. The Drive trash
protects deletions for thirty days; it does not protect replacements. The
user was told this before choosing, and chose it knowingly.

**22 — A first install says what it is.** The defaults were already clean,
but the app did not *say* so: a stranger saw an empty grid and no guide.
The guide now opens by itself when there is no client, and a test pins that
no source file names a drive letter or one of the four folders the app was
first built for.

## After the multi-account work

The app now holds several Google accounts. The decisions below were settled
with the user, by question and answer, on 2026-10-22. The full list is in
`docs/superpowers/specs/2026-10-22-drive-mirror-multi-account-design.md`,
section 5; these are the ones that cost something.

**23 — One account per app, always, is no longer true.** The app holds
several. Each account is a separate world: its own folders, its own
schedule, its own file list, its own sign-in, its own manifest. *Cost if
wrong:* the layout on disk is a folder per account rather than one file,
and every setting has to say whose it is.

**24 — The client id is entered once and shared by every account.** The
client id identifies the app, not the person, so a second account costs a
sign-in rather than another trip to the Google Cloud console. *Cost if
wrong:* one setting for the whole app, so two people sharing an install
cannot use different client ids.

**25 — The same local folder may be mirrored into two accounts.** They are
two independent mirrors with two separate file lists. *Cost if wrong:* a
mistake is made twice instead of once, and a file deleted on the disk is
trashed on both Drives.

**26 — Forgetting an account deletes it for good.** The account's folder and
its scheduled task go. The copies of its manifest in the backup folders
stay, so the file list can be recovered by hand. *Cost if wrong, and it is
a real one:* the app forgets which files it uploaded, so adding the same
folder again re-uploads everything and Drive ends up with duplicates. The
user was offered archiving instead and chose a permanent delete.

**27 — A Google account whose address changes becomes a different account.**
The old account stays signed out with its folders, and a new empty account
appears. The dropdown shows every account with its address and its folder
count, so the situation is visible, but the app does not guess. *Cost if
wrong:* the user has to work out what happened. The user was offered to
rebind the history and chose always-new.

**28 — A busy lock is waited out, and a skipped run is marked.** A run that
arrives while another account is syncing waits up to five minutes, and says
"waiting" while it does. A run that is finally given up on carries
`skipped`, and the schedule's clock does not move, so the slot is caught up
at the next tick. *Cost if wrong:* a run can be delayed by the length of
the other account's sync. This is also the fix for a live bug: the
scheduler used to advance its clock after any run that returned without
throwing, and a run that never happened returns just like one that did, so
a scheduled slot was silently lost.

**29 — The settings split, the migration and the registry are one change.**
The settings split alone breaks four source files and four test files; the
migration cannot run before the settings are rewritten or the legacy
folders and schedule are gone; and the sign-in has to be able to make an
account. Decided: one change. *Cost if wrong:* a large change that a
reviewer has to accept as a unit.

## Left for later

- The recovered file's path is the canonical, lower-cased one, so the
  original casing of a recovered file is lost. That is a property of the
  retired record, not of the download.
- `moveMirrorDestination` and `downloadRestored` write the manifest without
  taking the lock, so a run happening at the same moment can overwrite the
  change. The change is lost, not the data, and the user can make it again.
- The scheduler's `catchUpIsDue` and the core's `isRunMissed` answer
  different questions — a schedule that has never run has nothing to catch
  up on — but the two look like a disagreement.
